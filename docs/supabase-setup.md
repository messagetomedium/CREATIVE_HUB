# Подключение Supabase: аккаунты Creative Factory

**Сейчас по умолчанию активен локальный demo.** Эта инструкция относится к сохранённому реальному адаптеру. Для его включения установите `VITE_ACCOUNT_MODE=supabase` локально или в GitHub Repository Variables и пересоберите сайт; подробности — [demo-mode.md](demo-mode.md). Без этого Supabase-параметры намеренно не используются.

26 октября 2026 года. Код работает с настоящим Supabase Auth и Postgres через `@supabase/supabase-js`. Проект Supabase и SMTP пока **не созданы/не настроены**: реальная доставка email, hosted RLS с реальными JWT и вход двух настоящих пользователей ещё не проверены. Без параметров открываются главная и локальная прогулка, а экран входа честно сообщает о недоступной интеграции.

## 1. Создать проект и применить схему

1. Создайте отдельный dev-проект на [supabase.com](https://supabase.com/dashboard). Сохраните пароль БД вне репозитория. Для production позже используйте отдельный проект.
2. В **SQL Editor** выполните целиком [202610260001_accounts.sql](../supabase/migrations/202610260001_accounts.sql). Это первоначальная миграция: повторно применять её к уже созданным таблицам нельзя. Дальнейшие изменения оформляйте новыми миграциями.
   Затем выполните [202610270001_avatar_constructor.sql](../supabase/migrations/202610270001_avatar_constructor.sql): он добавляет валидацию новых выборов конструктора. Для уже созданных таблиц применяйте только эту новую миграцию, не повторяя первоначальную. Политики доступа и RPC остаются прежними.

3. В **Data API** оставьте API включённым и схему `public` доступной. Проверьте, что созданы `profiles`, `profile_private`, `avatar_configs`, функции `save_profile` и `save_avatar`; у таблиц включён RLS.
4. Не отключайте RLS и не добавляйте политики с записью для всех. Миграция уже выдаёт нужные grants. Профиль и внешность читают только зарегистрированные участники, меняет владелец; `profile_private` читает и меняет только владелец. Удаление через браузер не разрешено.

Идентичность — `auth.users.id` → `user_id`. Имя и фамилия не уникальны. `professional_role` принимает только `expert`/`educator` и не управляет разрешениями. Email остаётся в Auth и не дублируется в публичных/приватных таблицах приложения. `profile_private` сейчас содержит только настройку `locale`, создаётся вместе с первым сохранением профиля; отдельного UI для неё пока нет.

Сохранения идут через `SECURITY INVOKER` RPC под JWT пользователя и RLS. Создание использует expected revision 0, обновление — прочитанную revision; конфликт получает SQLSTATE `40001`. Триггер увеличивает revision и updated_at атомарно. Клиент не может передать другой user_id или изменить revision/created_at напрямую. Каталог v1 и ограничения длины проверяются также в БД. При расширении каталога нужно согласованно обновить контракт, графику и новую миграцию проверки разрешённых IDs.

## 2. Включить Email OTP

В **Authentication → Sign In / Providers → Email** (названия разделов могут отличаться в Dashboard):

1. Включите Email provider и регистрацию новых пользователей; подтверждение email должно быть включено.
2. Установите **Email OTP expiration = 600 секунд** и **OTP length = 6**, если поле длины доступно в вашей версии Dashboard. Если используется другая длина, задайте такое же значение `VITE_AUTH_OTP_LENGTH` (поддерживаются 6–10 цифр). Не путайте одноразовый код с password.
3. Оставьте ограничение повторной отправки не меньше **60 секунд**. Интерфейс выдерживает 60 секунд, дополнительные лимиты сервера показывает как ошибку с предложением подождать.
4. В **Email Templates** замените содержимое **Magic Link** и **Confirm signup** на письмо с `{{ .Token }}`. Не используйте `{{ .ConfirmationURL }}` как основной способ входа в этом приложении.

Пример собственного шаблона для обоих писем:

```html
<h2>Ваш пропуск в Creative Factory</h2>
<p>Введите на сайте одноразовый код:</p>
<p style="font-size: 32px; letter-spacing: 6px;"><strong>{{ .Token }}</strong></p>
<p>Код действует 10 минут и подходит только для одного входа.</p>
<p>Если вы не запрашивали код, просто проигнорируйте письмо.</p>
```

Тема: `Код входа в Creative Factory`. Если меняете срок действия, обновите текст письма и `VITE_AUTH_OTP_EXPIRY_SECONDS` вместе с настройкой Auth. Отсчёт в UI начинается после успешного ответа отправки; окончательную действительность/одноразовость всегда определяет Supabase, а не таймер браузера.

Код вызывает `signInWithOtp({ email, options: { shouldCreateUser: true } })`, затем `verifyOtp({ email, token, type: 'email' })`. Один и тот же путь создаёт аккаунт при первом визите и входит в существующий. Постоянных цифровых паролей нет. Ошибка OTP не подтверждает доставку или существование аккаунта.

## 3. Настроить настоящий SMTP

В **Authentication → Emails → SMTP Settings** включите **Custom SMTP**:

1. У выбранного почтового провайдера подтвердите домен отправителя и настройте DNS SPF/DKIM; настройте DMARC по инструкции провайдера.
2. Укажите sender email на подтверждённом домене и sender name `Creative Factory`.
3. Заполните host, port, username, password и параметры TLS по инструкции провайдера. Эти credentials вводятся **только в Dashboard Supabase**, не в `.env` web и не в GitHub variables.
4. Проверьте ограничения провайдера и Auth rate limits. Встроенная тестовая отправка Supabase имеет ограничения адресатов и квоты; она не заменяет настроенный SMTP для пользовательского приложения.
5. Отправьте код на настоящий адрес, проверьте папку спама, ввод кода, повторную отправку и Auth/SMTP delivery logs. Не публикуйте содержимое писем, коды или токены в логах приложения/issue.

Документация: [Email OTP](https://supabase.com/docs/guides/auth/auth-email-passwordless), [Email templates](https://supabase.com/docs/guides/auth/auth-email-templates), [Custom SMTP](https://supabase.com/docs/guides/auth/auth-smtp).

## 4. URL и публичные параметры web

В **Authentication → URL Configuration**:

- Site URL: `https://messagetomedium.github.io/CREATIVE_HUB/`.
- Допустимые redirect URLs для разработки: `http://localhost:5173/`, `http://127.0.0.1:5173/`; для публикации — точный адрес сайта и, при использовании, `https://messagetomedium.github.io/CREATIVE_HUB/site/`.
- Текущий flow вводит код прямо на сайте и не требует redirect/callback route. `detectSessionInUrl: false` исключает конфликт auth-фрагментов с hash routing. Не рассылайте magic-link вместо кода.

В **Project Settings → API / API Keys** скопируйте **Project URL** и **publishable key** (`sb_publishable_…`). `secret`/`service_role`, пароль БД, SMTP password и JWT signing secret не нужны браузеру. Legacy anon JWT эта версия конфигурации намеренно не принимает: используйте современный publishable key.

Для локального запуска:

```sh
cp .env.example .env
# Заполните .env в корне: VITE_SUPABASE_URL и VITE_SUPABASE_PUBLISHABLE_KEY.
npm ci
npm run dev
```

Корневой `.env` читается Vite; после изменения перезапустите dev server. Он игнорируется Git. Сессия хранится SDK в localStorage и обновляется штатным Auth refresh. Для выхода отзывается refresh-сессия этого браузера; при недоступном Auth локальные credentials удаляются и SDK перезапускается. Уже выданный access JWT живёт до своего expiry; это штатное ограничение JWT, не мгновенный отзыв всех токенов. Другие вкладки получают событие выхода и закрывают завод. Общий компьютер: нажимайте «Выйти» после работы.

## 5. Опубликовать подключённую версию

Выберите один способ, соответствующий текущему Source в **Settings → Pages**:

- **Deploy from a branch, main / (root)**: с заполненным локальным `.env` выполните `npm run export:pages`, затем закоммитьте и отправьте `index.html`/`site/` вместе с исходниками. В сборку входят только публичные параметры; `.env` не коммитьте.
- **GitHub Actions**: установите Source **GitHub Actions**. В **Settings → Secrets and variables → Actions → Variables** создайте `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY`, при необходимости `VITE_AUTH_OTP_EXPIRY_SECONDS=600` и `VITE_AUTH_OTP_LENGTH=6`. Запустите workflow **Publish Creative Factory to GitHub Pages**. Он подставляет именно эти публичные variables при сборке. Административные ключи туда не вводите.

Variables влияют только на новую Actions-сборку, они не меняют уже закоммиченный `site/` для веточной публикации. Если используете Actions с новыми variables, не переключайте затем Source на старый веточный экспорт без его обновления.

Hash-адреса `/#/login`, `/#/profile`, `/#/avatar`, `/#/factory` работают после reload без server rewrite. Полный пример: `https://messagetomedium.github.io/CREATIVE_HUB/#/avatar`.

## 6. Ручная приёмка после настройки

1. В двух отдельных профилях браузера зарегистрируйте A и B с разными реальными email. Одинаковые имя/фамилия допустимы.
2. Пройдите код → имя/фамилия → сохранение профиля → редактор → сохранение → завод. Перезагрузите страницу, выйдите и войдите повторно: профиль и внешность должны восстановиться.
3. Проверьте неверный/истёкший код, resend, ошибку SMTP и недоступный Supabase. Email не должен появляться в ответах `profiles`.
4. Через Data API с anon key без JWT убедитесь в запрете чтения всех трёх таблиц. С JWT A разрешён SELECT публичного профиля/внешности B, но UPDATE B и чтение `profile_private` B должны быть запрещены/возвращать пустой результат. Чужой INSERT и UPDATE user_id запрещены. Проверяйте именно пользовательскими JWT: SQL Editor/table editor от имени владельца БД обходят обычный RLS и для этой проверки не подходят.
5. Откройте профиль/аватар в двух вкладках, сохраните в первой, затем попробуйте сохранить старую форму во второй: должен быть конфликт, а не тихая перезапись.
6. Подтвердите отсутствие приватных credentials в опубликованных JS и отсутствие токенов/email в логах приложения. Публичный publishable key виден в браузере по назначению и работает только вместе с RLS.

Автоматический `npm test` уже выполняет настоящие SQL-ограничения/RLS в PGlite (PostgreSQL WASM), подставляя `auth.uid()` через контролируемые claims. Chromium E2E используют настоящий Supabase SDK с перехваченными HTTP-ответами. Это воспроизводимые проверки приложения и политик, но они не подтверждают настройки вашего hosted-проекта, проверку JWT сервисом или доставку email.
