# WorkAdventure: технический референс для Creative Factory

Дата аудита: 23 октября 2026 года. Статус: статическое исследование исходников и документации; WorkAdventure не запускался, его тесты не выполнялись. Результат — спецификация для самостоятельной реализации, а не оценка готовности нашего ещё не реализованного приложения.

## Существенные технические выводы

### Карты: формат, глубина и производительность

Важна разница между порядком слоёв карты и глубиной подвижных объектов. Пол должен находиться ниже ног персонажа, навесы — выше, а отдельные высокие предметы — сравниваться с персонажем по координате основания. В WA `Character` обновляет depth по Y, а обёртка карты делит слои относительно `floorLayer`. Для нашего формата нужен собственный явный контракт глубины; простое «вся мебель поверх игрока» не позволит корректно обходить станок с разных сторон.

В текущем `GameMapFrontWrapper` есть выбор `TilemapGPULayer`, но только для подходящих слоёв: учитываются пригодность tileset и плотность. Разреженные верхние слои могут быть дешевле в обычном рендерере. Следовательно, переход на GPU-слой сам по себе не является оптимизацией. В первом прототипе достаточно стандартного tilemap renderer, camera culling и атласов.

Документ `wa-maps.md` содержит старое обобщение об игнорировании object layers, тогда как актуальные исходники и документы зон работают с объектами-областями. Не переносить это ограничение в наш формат. Аналогично документация рекомендует встроенный редактор WA для части возможностей; для Creative Factory достаточно внешнего Tiled.

Для tile-анимаций [документация][tile-animation-doc] упоминает обновление раз в 100 мс, но текущий `GameMapFrontWrapper.getTilesetAnimationRefreshDelay` вычисляет интервал по длительностям кадров и ограничивает его снизу 16 мс. Это ещё одна причина проверять версию исходников, а не переносить исторические ограничения документации в свой движок.

### Движение: что именно проверено

В `Player.inputStep/moveBy` задаётся клиентская скорость; `GameScene.createCollisionWithPlayer` настраивает столкновения с плитками. В `back/SocketManager.handleUserMovesMessage` проверяются наличие position/viewport и перегрузка CPU, после чего вызывается `room.updatePosition`. Это подтверждает модель пересылки клиентской позиции в изученном пути, **не** полноценный аудит всех защит платформы.

Для нашего продукта серверная симуляция усложняет MVP, но даёт единые коллизии, проверку порталов и защиту от произвольных телепортов. Одна чистая TS-функция шага движения должна использоваться сервером и клиентским prediction; повторять физику отдельно через Phaser Arcade на клиенте и другую математику на сервере не следует.

### Сеть: сглаживание не равнозначно авторитетному состоянию

WA сглаживает движение к уже полученной координате на следующем интервале. Это не то же самое, что интерполяция двух серверных снимков по общей временной шкале. В нашем проекте предлагаем второй вариант: хранить несколько последних позиций и отображать удалённых игроков с небольшим отставанием относительно server time. Для себя — prediction и поправки по ack.

В исходнике `MAX_EXTRAPOLATION_TIME = 100`, хотя рядом оставлен комментарий про 250 мс. Вывод сделан по значению константы и прочитанным тестам, а не по комментарию. Тесты WA прочитаны, но не запускались; они не являются результатом проверки Creative Factory.

Интерес к зоне, видимость в камере и онлайн-присутствие — разные понятия. Исчезновение из области интереса не означает выход пользователя из завода. Удалённый аватар нужно убирать также из очереди интерполяции, загрузчиков/подписок и интерактивных обработчиков, иначе возможны повторное появление и утечки.

### Разрывы: требование «аватар исчезает»

В WA неожиданный обрыв может удерживать логическую сессию для восстановления; нормальные close-коды приводят к окончательному cleanup. В Creative Factory требование строже для видимого мира: явный выход удаляет аватар немедленно после обработки сервером; сетевой обрыв — после его обнаружения heartbeat/transport. Мгновенно отличить молчаливый обрыв от задержки сети нельзя. В предлагаемой архитектуре сохранение позиции для reconnect не сохраняет видимого персонажа.

Общее правило разработки: переносим только сформулированные требования и общеупотребительные принципы — tilemap, слои, пространственная сетка, интерполяция, heartbeat. Это самостоятельная реализация по технической спецификации; формальная clean-room-разработка с независимыми командами этим аудитом не доказана.

## Что взять и что упростить

Сохранить выбранный стек **React + TypeScript + Phaser + Colyseus + Supabase + Tiled**. Более простым будет не отказ от этого стека, а меньшее число сервисов и функций: одна FactoryRoom, одна карта, небольшой каталог своих аватаров, React-профили, статическая публикация контента. Colyseus заменяет самостоятельную разработку сервера комнат, состояния и lifecycle, но не collision solver и не сглаживание изображения.

Вариант Supabase Realtime без Colyseus уменьшил бы число развертываемых сервисов, но не предоставил бы авторитетный цикл движения и согласованную проверку коллизий. Самописный WebSocket-сервер потребовал бы заново проектировать lifecycle, snapshots и восстановление. Для заданной цели оба упрощения хуже выбранного Colyseus.

Оставшиеся проверки перед реализацией: совместимость версий Phaser/Colyseus, поведение filtered state при reconnect, права на будущие ассеты, реальные бюджет кадра/сети и лимит одновременных посетителей. Никакие показатели производительности приложения этим статическим аудитом не измерены. Следующие решения и критерии находятся в [architecture.md](architecture.md) и [implementation-plan.md](implementation-plan.md).
